## 1. 背景と目的

### 1.1 RoomRadar とは
学生が「いま空いている教室」を曜日・時限・校舎から即座に探せる Web アプリ。
時間割データ上で「その曜日・時限に授業が入っていない教室＝空き」とみなして一覧表示する。
加えて、学生同士で使える軽量な **仮予約**（RoomRadar 上のみ）と、
「実は使われていた」を共有する **クラウドソース報告** 機能を持つ。

### 1.2 なぜ全国対応か
仕組み自体は「時間割さえあれば」どの学校でも成立する。
現状は日大理工に固有の情報がコードへ埋め込まれているため横展開できないだけで、
**設定とデータを外部化すれば全国の大学・専門学校・高校へ展開可能**。

### 1.3 ゴール
- 1つのコードベース／1つのデプロイで **複数校** をホストできる。
- 新しい学校の追加が **「データを追加するだけ（コード変更不要）」** で完了する。
- 学生が **自分の学校分を無理なく提供・メンテ** できる導線を持つ。

## 2. 現状分析

### 2.1 リポジトリ構成（`csko24143-droid/nust-room-search`）

| ファイル | 役割 |
|---|---|
| `app.py`（約1,200行） | Flask 動的バックエンド。検索＋仮予約＋報告。テンプレHTMLを文字列で内包。Render系想定（PORT 10000） |
| `index.html`（約68KB） | 静的版（別デザイン・ライトテーマ）。GitHub Pages 公開 (`…github.io/nust-room-search`) |
| `dashboard.html` | Chart.js のアナリティクス画面（Instagram インサイト等） |
| `schedule_final.db` | 時間割DB。`schedules`（13,614行）＋ `classrooms`（181室） |
| `classroom_data.xlsx` / `summry_classrooms.xlsx` | 元データ（Excel） |
| `scripts/*.py` ＋ `.github/workflows/instagram-*.yml` | Instagram 自動投稿・インサイト取得 |
| `reservations.db` / `reports.db` | 実行時生成（gitignore）。仮予約・報告の揮発データ |

### 2.2 データモデル（現状）
- `schedules(id, 学科, 履修期名, 曜日, 時限, 教室, 校舎, 科目名)` — 履修期名は `前期/後期`。
- `classrooms(name, building)` — 校舎は `タワースコラ / 駿河台校舎 / 船橋校舎` の3種（計181室）。
- 空き判定ロジック: 指定 `曜日・時限`＋有効学期で `schedules.教室` を集めて「使用中集合」を作り、`classrooms` の全室から差集合を取る（`app.py` の `index()`）。

### 2.3 「全国対応」を阻むハードコード箇所

| カテゴリ | 直書きされている内容 | 影響箇所 |
|---|---|---|
| 学校アイデンティティ | 「RoomRadar — 日大理工」「日大理工学部」ロゴ・公開URL | `HTML_TEMPLATE`、`index.html` |
| 校舎 | `tower / main / funabashi`、表示名、**色**、並び順 | `VALID_BUILDINGS`、テンプレの3セクション、`empty_rooms` ソートキー |
| 時限 | 6限・固定時刻 | `PERIODS`（Python）＋ JS 側 `PERIODS` |
| 学期 | `前期/後期/通年`、境界日 `4/1〜9/20` | `ACTIVE_TERMS`, `get_active_terms()` |
| 曜日 | `月〜土` | `VALID_DAYS`、テンプレ |
| 解析・SNS | GAタグ `G-…`、Instagram 各アカウント | テンプレ、workflows |

### 2.4 既知の不具合・負債（移行時に解消する）
- **時限時刻の二重定義・不一致**: Python 側 `1限=09:00–10:40` に対し、JS 側は `1限=09:00–10:30`。
  片方は予約の有効期限計算、片方は「現在時限」判定に使われ、**ズレている**。
  → 時限時刻は **学校設定の単一ソース** から両者へ供給する（§8）。
- **フロントが2系統**（`app.py` 内テンプレ と 静的 `index.html`）でデザイン・挙動が分岐。→ 統合方針を §9 に定義。
- 仮予約・報告に **学校スコープが無い**（全校共有の `room/day/period` キー）。マルチテナントでは衝突する。→ §5.4。

## 3. 設計目標とスコープ

### 3.1 ねらい（Goals）
- **テナント分離**: すべての学校固有情報を設定・データへ外部化。コードは学校非依存。
- **追加コストの最小化**: 新規校はファイル追加（＋自動取り込み）だけ。サーバ運用費は学校数にほぼ依存しない。
- **貢献しやすさ**: 学生が自校の時間割を所定フォーマットで提出できる。
- **後方互換の移行**: 既存の日大理工版を「最初のテナント」として無停止で載せ替え。

### 3.2 やらないこと（Non-Goals・初期段階）
- 大学公式の予約システムとの連携／公式予約の代替（あくまで非公式・情報共有）。
- 個人アカウント・ログイン基盤（仮予約は匿名＋キャンセルコード方式を継続）。
- 全学校をWeb管理画面から非技術者が編集する自己管理SaaS（将来フェーズで検討）。
- 時間割の自動スクレイピング（権利・形式リスク。§15参照）。

## 4. アーキテクチャ全体像

### 4.1 中心となる考え方：「静的コア」＋「薄い動的レイヤ」の分離

空き教室の計算は **時間割（不変データ）＋現在時刻だけ** で決まる純粋関数であり、
ユーザー入力で状態が変わるのは **仮予約・報告だけ**。そこで2層に分離する。

```
┌──────────────────────────────────────────────────────────┐
│  静的コア（学校ごと・キャッシュ可能・サーバ不要）          │
│   - 学校設定 (config)                                      │
│   - 時間割 / 教室データ（コンパクトなJSONに事前ビルド）      │
│   - 空き判定はブラウザ側で計算 → 学校が増えても負荷増えない  │
└──────────────────────────────────────────────────────────┘
                    │  仮予約・報告のみ API 呼び出し
                    ▼
┌──────────────────────────────────────────────────────────┐
│  動的レイヤ（全校共通の小さなバックエンド）                 │
│   - /api/{school}/reserve, /report （school スコープ付き）  │
│   - 揮発DB（時限終了で自動失効）。負荷は予約数のみに比例     │
└──────────────────────────────────────────────────────────┘
```

メリット:
- **スケール**: コア機能（検索）はCDN配信＋クライアント計算でほぼ無限にスケール。
- **コスト**: 動的バックエンドは1つだけ（無料〜低価格帯のホスティングで足りる）。
- **堅牢性**: バックエンドが落ちても「検索」は静的に動く（予約・報告だけ一時停止）。

> 注: 既存 `app.py` はサーバ側でHTMLを描画する構成。上記は「検索の計算をクライアントへ寄せる」方向で、
> §9 のフロント統合と合わせて段階的に移行する（フェーズ1では既存方式のままテナント化してもよい）。

### 4.2 論理コンポーネント
- **School Registry**: 全校の一覧（slug・名称・地域・公開状態）。トップページの検索/一覧に使用。
- **School Config**: 学校ごとの buildings / periods / terms / days / theme / analytics。
- **Timetable Store**: 学校ごとの時間割・教室データ。
- **Availability Engine**: 設定＋時間割から空き教室を算出（クライアント or サーバ）。
- **Live Layer**: 仮予約・報告（school スコープ付き）。
- **Onboarding Pipeline**: CSV/Excel → 検証 → 配信用データへ変換（§7）。

## 5. データモデル

### 5.1 学校レジストリ `schools/index.json`
```json
[
  { "slug": "nust", "name": "日本大学 理工学部", "short": "日大理工",
    "region": "東京・千葉", "status": "active" },
  { "slug": "example-u", "name": "○○大学", "short": "○○大",
    "region": "大阪", "status": "beta" }
]
```
- `slug`: URL・APIキー・データフォルダ名に使う一意ID（英小文字・ハイフン）。
- `region`: 全国一覧・都道府県での絞り込み用。
- `status`: `active` / `beta` / `hidden`。

### 5.2 学校別設定 `schools/<slug>/config.yml`
**ハードコード一覧（§2.3）をそのまま設定項目に対応付けたもの。**
```yaml
slug: nust
name: 日本大学 理工学部
short_name: 日大理工
region: 東京・千葉
timezone: Asia/Tokyo
theme:
  accent: "#6c8fff"          # 学校テーマ色
days: [月, 火, 水, 木, 金, 土]

# 時限は「単一ソース」。サーバ・クライアント双方がここを参照する。
periods:
  - { no: 1, start: "09:00", end: "10:40" }   # ※現行2系統で時刻が不一致。要確認(§2.4)
  - { no: 2, start: "10:50", end: "12:30" }
  - { no: 3, start: "13:20", end: "15:00" }
  - { no: 4, start: "15:10", end: "16:50" }
  - { no: 5, start: "17:00", end: "18:40" }
  - { no: 6, start: "18:50", end: "20:30" }

terms:
  - { id: 前期, start: "04-01", end: "09-20" }
  - { id: 後期, start: "09-21", end: "03-31" }
  - { id: 通年, always: true }

buildings:
  - { id: tower,     name: タワースコラ, color: "#6c8fff" }
  - { id: surugadai, name: 駿河台校舎,   color: "#4dd9a0" }
  - { id: funabashi, name: 船橋校舎,     color: "#ff8c5a" }

analytics:
  ga4: ""                    # 学校ごとに任意（空なら計測なし）
```
> 完全な記入例は [`examples/nust.config.yml`](./examples/nust.config.yml)。

### 5.3 時間割・教室データ（CSV）
学校ごとに2ファイル。Excel でも可（取り込み時に CSV 化）。

`schools/<slug>/schedule.csv`（時間割）:
```csv
department,term,day,period,room,building,course
物理学科,前期,月,2,123,タワースコラ,力学I
```
`schools/<slug>/classrooms.csv`（教室マスタ。任意。無ければ時間割から自動生成）:
```csv
room,building
123,タワースコラ
```
- 列名は英語で固定（多言語・表記ゆれを避ける）。`building` の値は config の `buildings[].name` と一致必須（検証で担保）。
- 詳細仕様とテンプレは [`data-import-format.md`](./data-import-format.md)。

### 5.4 動的データ（予約・報告）に school スコープを追加
既存スキーマへ `school` 列を追加し、複合キーへ。
```sql
-- reservations
CREATE TABLE reservations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  school TEXT NOT NULL,            -- ★追加
  room TEXT, building TEXT, day TEXT, period INTEGER,
  name TEXT, purpose TEXT,
  cancel_code TEXT NOT NULL,
  created_at TEXT NOT NULL, expires_at TEXT NOT NULL
);
CREATE INDEX idx_res ON reservations(school, day, period, room);  -- ★school 先頭

-- reports も同様に school 列＋ (school, day, period, room) インデックス
```
- フロントの localStorage キーも `reserve_{school}_{room}_{day}_{period}` へ拡張。
- 失効ロジック（時限終了で自動 DELETE）は現行を踏襲。

## 6. ルーティングとテナント解決

| 方式 | 例 | 長所 | 短所 | 採否 |
|---|---|---|---|---|
| **パス方式** | `roomradar.app/s/nust` | 1ドメイン・1証明書で完結。実装最小 | URLが少し長い | **採用（推奨）** |
| サブドメイン | `nust.roomradar.app` | 学校ごとに“自分のサイト”感 | ワイルドカードDNS/TLS・運用増 | 将来オプション |
| クエリ | `?school=nust` | 最も簡単 | 共有/SEO/見た目で不利 | 不採用 |

ルート構成（パス方式）:
- `/` … **全国トップ**。学校を名称・地域で検索／一覧 → 各校へ遷移。
- `/s/<slug>` … その学校の RoomRadar（検索画面）。
- `/api/<slug>/reserve` `/api/<slug>/report`（＋ `/cancel`, `/list`）… 動的レイヤ。
- 未知の `slug` は 404 ＋ 学校一覧へ誘導。

## 7. データ投入パイプライン（推奨方式と根拠）

> ユーザー判断は「Claude に任せる」。以下を**推奨方式**として採用する。

### 7.1 推奨：ファイル方式（設定YAML＋時間割CSV）をリポジトリ管理
理由:
- **限界コストがほぼゼロ**: 学校が増えてもファイルが増えるだけ。サーバ・DB運用が膨らまない（無料ホスティングと好相性）。
- **透明性・レビュー性**: 変更履歴が git に残り、PR でレビューできる。誤った時間割の混入を防げる。
- **貢献しやすさ**: 「テンプレに沿って自校分を出す」だけ。技術が苦手な学生は後述のフォーム/Issue で代理取り込み。
- **既存資産と整合**: 現状すでに Excel→DB のバッチ運用。これを所定フォーマット＋検証付きに整えるだけで延長線上。

非技術者の編集が前提になる規模（数百校＋頻繁な更新）になったら、§14 フェーズ3で **管理UI＋DB** へ拡張する（ファイル方式を“真実の源”に保ったままインポート経路を足す）。

### 7.2 取り込みフロー
```
学校の時間割(Excel/CSV)
   │  ① 提出（PR / Issueテンプレ / Googleフォーム → 代理コミット）
   ▼
schools/<slug>/{config.yml, schedule.csv, classrooms.csv}
   │  ② 検証 scripts/validate.py（CIで自動実行）
   │     - 必須列・型・建物名整合・時限/曜日の妥当性・重複検出
   ▼
   │  ③ ビルド scripts/build.py
   │     - schedule.csv → 配信用 schedule.<slug>.json（コンパクト化）
   │     - 全 config → schools/index.json
   ▼
配信（静的ホスティング/CDN）＋ 動的レイヤは school 列で共用
```

### 7.3 貢献者向けの導線
- `CONTRIBUTING.md` に「自校を追加する手順」を明記。
- `.github/ISSUE_TEMPLATE/add-school.yml`（学校追加リクエスト）。
- 非技術者向けに Google フォーム/スプレッドシート版テンプレ → メンテナが CSV 化してコミット。

## 8. バックエンド・リファクタ方針

`app.py` を「学校非依存のエンジン」に作り替える。

1. **設定ローダ**: 起動時に `schools/*/config.yml` と `index.json` を読み込み、`SCHOOLS[slug]` として保持（メモリキャッシュ＋ファイル監視 or デプロイ時確定）。
2. **検索の汎用化**: 現状の校舎別 `if building == 'tower' …` 分岐を撤去し、
   `buildings` を設定から動的生成。空き判定は
   「`schedules` の使用中集合（school・term・day・period）」と「`classrooms`（school）」の差集合、で学校非依存化。
3. **時刻の単一ソース化**: `PERIODS`（Python）と JS の時刻定義を廃し、**config の `periods`** をサーバ→テンプレ→JS へ一方向に供給。§2.4 の不整合を根絶。
4. **学期判定の汎用化**: `get_active_terms()` を config の `terms[].start/end/always` から算出する純粋関数に置換。
5. **API の school 化**: 受け口を `/api/<slug>/…` にし、入力検証は「その学校の days/periods/buildings 集合」に対して行う（現行のグローバル `VALID_*` を学校別に）。
6. **テンプレのトークン化**: 校舎セクションを `{% for b in buildings %}` でループ化。色は CSS 変数に流し込む。学校名・サブタイトル・GAタグも変数化。
7. **レート制限**: 現行のIPベースを踏襲しつつ、キーに school を含めて学校間の相互影響を排除。

> フェーズ1では「サーバ描画のまま汎用化」、フェーズ2で「検索のクライアント計算化（§4.1）」へ段階移行する。

## 9. フロントエンド方針

### 9.1 2系統フロントの統合
現状 `app.py` 内テンプレ（ダーク）と静的 `index.html`（ライト）が併存。
**1つの実装に統合**し、テーマはトークン（CSS変数）で切替可能にする。
- 方針A（推奨）: 検索UIを静的SPA化し、学校データJSONを読んでクライアントで空き計算。予約/報告だけ API。→ §4.1 と一致、CDN配信でスケール。
- 方針B: 当面は `app.py` のサーバ描画に一本化（実装が早い）。フェーズ2でAへ。

### 9.2 全国トップページ（新規）
- 学校検索（名称・地域・略称）、人気/近隣のサジェスト、`status=beta` バッジ。
- 「自分の学校を追加する」CTA → `CONTRIBUTING` / Issue テンプレへ。

### 9.3 学校テーマ
- アクセント色・校舎色を config から注入。ロゴはデフォルト＋学校別差し替え可。
- アクセシビリティ（コントラスト比、フォーカス可視、`prefers-reduced-motion`）を統合時に担保。

## 10. スケーラビリティと性能

- **検索**: クライアント計算＋CDN（§4.1）で学校数・閲覧数に対しスケール。時間割JSONは学校単位で分割ロード（必要な学校だけ取得）。
- **動的レイヤ**: 予約・報告のみ。SQLite は当面十分。規模拡大時は
  (a) 学校ごとにDBファイル分割、または (b) Postgres へ移行（`school` 列で水平分割可能な設計を最初から採用）。
- **キャッシュ**: 時間割JSON・config は長めのキャッシュ＋デプロイ時バージョニング（ファイル名にハッシュ）。
- **データ鮮度**: 学期切り替え・時間割改訂時のみ再ビルド。日次の再生成は不要。

---

## 11. セキュリティとプライバシー

- **入力検証**: day/period/building/room を**その学校の許可集合**に対して検証（現行のグローバル検証を学校別へ）。長さ制限は踏襲。
- **PII（個人情報）**: 仮予約の「お名前/グループ名」は任意入力だが個人が特定され得る。
  - UIで実名非推奨を明示、最大長制限、時限終了で自動削除（現行通り）。
  - 必要に応じ表示を伏せ字/イニシャル化、保持期間の最小化。
- **XSS**: テンプレは自動エスケープを徹底（`render_template_string` のまま可だが、ユーザー入力をDOM挿入する箇所は `textContent` を使用）。
- **濫用対策**: school 込みのレート制限、報告の闾値（現行2件→学校別に調整可）、キャンセルコード方式の継続。
- **データ出典の権利**: 時間割の取得元と再配布可否を学校ごとに確認（§15）。出典・更新日を学校ページに明記。

---

## 12. 解析・運用・SNS

- **解析**: GA4 タグを config 化（学校別 or 全体集約）。`dashboard.html` を「学校フィルタ付き」に一般化。
- **Instagram自動化**: 現行の `scripts/` ＋ workflows を「学校別アカウント設定」に対応するテンプレートへ（Secrets を学校別に）。全国展開では各校の運用体制が前提なので**任意機能**として分離。
- **監視**: 動的レイヤの稼働監視＋失効バッチの健全性チェック。

## 13. 移行計画（NUSTを最初のテナントに）

1. `schedule_final.db` の `schedules`/`classrooms` を `schools/nust/schedule.csv` / `classrooms.csv` へエクスポート。
2. §2.3 のハードコード値から `schools/nust/config.yml` を作成（時限時刻の不一致は学校に確認のうえ確定）。
3. リファクタ後エンジンで `slug=nust` を描画し、**現行サイトと同一結果**になることを回帰確認（曜日×時限×校舎の空き一覧を旧実装と突合）。
4. 仮予約・報告DBに `school='nust'` を付与してマイグレーション（既存揮発データは破棄でも可）。
5. 旧 `nust-room-search` から新 `Nationwide-RoomRadar` へ切替（リダイレクト or 告知）。

## 15. リスクと未解決事項

- **最大の課題はコードではなく「データ」**: 全国の時間割を**正確・最新**に保つこと。
  - 取得元（学校公式/シラバス）の**再配布可否・利用規約**を校ごとに要確認。スクレイピングは権利・形式変更リスクが高く非推奨。
  - **鮮度**: 学期・履修期で改訂される。改訂検知と再ビルドの運用設計が必要。
  - **維持体制**: 各校に提供/更新する担い手（学生メンテナ）をどう確保するか。
- **表記ゆれ**: 教室名・校舎名の表記が学校で不統一。検証（config の建物名と突合）で吸収。
- **時限・学期の多様性**: クォーター制、集中講義、休講日など例外。`terms`/`periods` スキーマの拡張余地を残す。
- **非公式であることの周知**: 「公式予約ではない」旨の免責を全校で明示（現行踏襲）。
- **未確定事項**:
  - 時限時刻の正しい値（Python版/JS版どちらが正か、学校に確認）。
  - 独自ドメインの有無（パス方式かサブドメインか）。
  - フロント統合の方針A/B（§9.1）の最終決定。

## 16. 付録：用語集

| 用語 | 意味 |
|---|---|
| テナント | このプラットフォーム上の1つの学校 |
