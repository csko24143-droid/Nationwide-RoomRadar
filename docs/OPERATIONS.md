# 運用ガイド（メンテナ向け）

全国展開で最大の課題は「コード」ではなく **データ（全国の時間割を正確・最新に保つこと）**
です（[DESIGN §15](DESIGN.md)）。この文書は継続運用の体制と手順をまとめます。

## 体制：各校メンテナ制度

- **1 校につき 1 人以上の学生メンテナ** を置くのが理想。自校の時間割を学期ごとに更新します。
- メンテナは GitHub アカウントを持ち、`schools/<slug>/` の更新 PR を出せること。
- 技術が苦手な提供者は [かんたん追加フォーム](../web/add-school.html) または
  Issue テンプレ「学校の追加リクエスト」で依頼 → 既存メンテナが代理取り込み。

## 更新サイクル（学期ごと）

1. 新学期の時間割を入手（公式・学務システム等。**再配布可否を確認**）。
2. `schools/<slug>/schedule.csv` を更新し、`config.yml` の `data_updated` を当日へ。
3. 検証 → ビルド → テスト:
   ```bash
   python scripts/validate.py --slug <slug>
   python scripts/build.py
   python -m unittest discover -s tests
   ```
4. PR を出す。CI（`.github/workflows/ci.yml`）が検証・ビルド・テストを自動実行。
5. マージ後、デプロイ（[DEPLOY.md](DEPLOY.md)）。

## データ鮮度の管理

- 運用ダッシュボード `/dashboard` の **鮮度** 列で各校の `data_updated` を一覧。
  既定で **180 日超は「要更新」バッジ**を表示します（基準は `_freshness_cell` で調整可）。
- 学校ページのフッターにも「データ最終更新・出典」を表示し、利用者へ鮮度を明示。

## データの権利・プライバシー

- 時間割の **入手元の利用規約・再配布可否** を校ごとに確認。スクレイピングは非推奨。
- 個人が特定される情報（実名等）は時間割データに含めない。
- 仮予約の任意入力（お名前/グループ）は実名非推奨を明示し、時限終了で自動削除。

## 解析・SNS（任意機能）

- **解析**: `config.yml` の `analytics.ga4` に学校別 GA4 タグを設定可（空なら計測なし）。
- **SNS 自動投稿**: 各校のアカウント運用が前提のため**任意機能として分離**。
  旧 `nust-room-search` の `scripts/` ＋ `.github/workflows/instagram-*.yml` を
  「学校別 Secrets」のテンプレートとして移植する想定（本リポジトリ未同梱）。

## バックアップ／障害時

- **学校データ**（`schools/`）は git が真実の源。バックアップ不要（履歴で復元可）。
- **予約・報告**は揮発データ（時限終了で自動失効）。SQLite なら再デプロイで消えるが、
  仕様上許容。永続化が必要なら Postgres（`DATABASE_URL`）。
- バックエンドが落ちても **検索（静的コア）は動作**し、予約・報告だけ一時停止します。
